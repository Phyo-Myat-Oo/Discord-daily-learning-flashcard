# Curriculum card generation

Create exactly the requested curriculum cards from the compact context below. Return only one JSON object with a `cards` array. Do not inspect or modify repository files, run commands, or add commentary. The caller validates and installs the cards.

Create one card for each listed `(stream, date, sequence)` slot. Copy its `sequence`, `stream`, and `required_difficulty` exactly, using `required_difficulty` as the card's `difficulty`. Use only an allowed category and set `status` to `approved`. Teach prerequisites before dependent concepts: beginner establishes vocabulary and safe basic workflows; intermediate applies them in realistic troubleshooting; advanced teaches tradeoffs, failure modes, security, performance, and operational judgment. A review may test only earlier sequence numbers. Every card must be atomic, practical, accurate, and comfortably under Discord's limits. Prefer operational knowledge over trivia. Avoid concepts equivalent to supplied covered topics and recent cards; a repeated subject is allowed only for a meaningfully deeper skill.

For a `neuroscience` slot, use `language: en`, include only `content.en`, teach exactly its `topic_focus`, use category `neuroscience`, and copy its complete `study_plan` object without modification. Ground factual claims in the supplied source excerpt. Never add extra required reading or extend its page range. The supplied online resource is an optional companion link, not additional required study time. Practical and review days still need one small teaching concept that prepares the assigned activity. Keep the English lesson concise enough to leave room for the study-plan embed; target at most 2,400 rendered characters.

When a neuroscience `study_plan.assessment` is present, generate exactly five `review_items` in the same order as its blueprint. Test mechanisms and application rather than vocabulary trivia. Answers must be concise enough for Discord spoilers. For neuroscience slots without an assessment, return `review_items: null`.

For every non-neuroscience slot, use `language: bilingual`; follow the supplied terminology guide; and write complete comprehension-first `content.en` and `content.my` blocks. Every rich language block is a mini-lesson, not a source summary. It requires `title`, one atomic `learning_objective`, a concrete `simple_explanation`, cause-and-effect `how_it_works`, `visual`, realistic `use_case`, observable `expected_result`, interpretive `what_to_notice`, genuine `common_mistake`, `practical_tip`, aligned `question`, and concise `answer`.

Draft and fact-check English first. Start from a familiar situation, define new terms before relying on them, and use short sentences. Then explain the same meaning independently in natural Burmese as a patient technical instructor; do not copy English sentence structure. Retain and explain familiar English technical terms according to the terminology guide. The example must give the learner something concrete to run, inspect, compare, or predict. `expected_result` states what happens; `what_to_notice` explains why that result matters. Do not repeat one paragraph under different headings.

The visual must teach the core relationship at a glance. Prefer a 2–6 line flow, state transition, comparison, hierarchy, or annotated command. No line may exceed 48 characters; prefer a vertical mobile layout over a wide horizontal flow. Keep the complete rendered description below 2,700 characters per language. Depth must come from reasoning and interpretation, not padding.

Before returning, silently check every card for factual accuracy, English/Burmese meaning alignment, schema completeness, progression, duplicate concepts, safe commands, diagram width, and distinct teaching sections. Follow the suggested category as a quality-oriented guide. The caller owns validation and state updates.
